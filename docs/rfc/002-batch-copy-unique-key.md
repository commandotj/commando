## 摘要

在文件管理器的批量复制功能中，原有实现采用 index 作为 key 和选中项标识，导致唯一性和路径准确性不足。本RFC提出使用绝对路径作为全链路唯一标识符的解决方案，彻底消除 index 依赖，保证复制操作的准确性和健壮性。

## 背景

### 问题描述
在文件管理器的批量复制功能中，原有实现采用 index 作为 key 和选中项标识，导致唯一性和路径准确性不足，存在如下问题：
- index 不是全局唯一，排序/过滤/多窗口等场景下可能重复或失效
- 复制操作链路中，index 传递导致路径拼接错误，可能出现无效路径
- 进度跟踪、UI 展示等依赖 index，易引发状态错乱

### 现状分析
- 选中项 selectedKeys、表格 key 字段、Modal 进度等均用 index，唯一性和准确性无法保证
- 复制时拼接路径出错，导致实际操作文件不符预期
- 缺乏统一的标识符管理机制

### 业务驱动
- 提升文件操作的准确性和可靠性
- 支持复杂的多选和跨目录操作
- 为后续扩展多批次、任务历史、并发等高级功能奠定基础

## 目标

### 主要目标
- [x] 彻底消除 index 依赖，保证唯一性和健壮性
- [x] 复制、进度、UI 展示等所有环节准确无误
- [x] 便于后续扩展多批次、任务历史、并发等高级功能

### 成功标准
- 所有文件操作使用绝对路径作为唯一标识
- 多选、全选、跨目录、排序、刷新等场景下复制与进度跟踪准确无误
- Redux 状态、UI 展示、进度消息与实际文件操作完全一致

## 提案

### 解决方案概述
采用绝对路径作为全链路唯一标识符，替代原有的 index 机制，确保从UI选择到文件操作的完整链路一致性。

### 技术方案
**方案一（已采纳）：全链路用绝对路径**
- FilePane 组件 dataSource 的 key 字段和 selectedKeys 全部用 joinPath(currentPath, entry.name) 生成的绝对路径
- 复制操作、进度跟踪、Modal 展示等全链路都用绝对路径，彻底消除 index 依赖
- Redux 状态、UI 展示、进度消息等全部以路径为唯一主线

**方案二（未采纳）：用文件名**
- 仅适用于无重名、单目录场景，无法满足复杂需求

### 实现细节

#### 核心实现要点
- **FilePane**: dataSource key/selectedKeys = joinPath(currentPath, entry.name)
- **FunctionBar**: 复制操作直接用 selectedKeys 作为源路径数组
- **BatchCopyProgressModal**: srcs、fileProgressList、key、进度消息 file 字段全部为绝对路径
- **Redux 状态**: UI、进度跟踪全链路唯一

#### 技术架构
```
用户选择 → FilePane (绝对路径key) → Redux状态 → FunctionBar → 复制操作 → 进度跟踪
```

## 影响分析

### 对现有系统的影响
- **正面影响**：
  - 彻底消除 index 依赖，保证唯一性和健壮性
  - 复制、进度、UI 展示等所有环节准确无误
  - 便于后续扩展多批次、任务历史、并发等高级功能
- **负面影响**：
  - 需要修改多个组件的实现逻辑
  - 路径字符串比数字index占用更多内存

### 兼容性分析
- 完全向后兼容，不影响现有功能
- 提供了渐进式迁移路径

### 性能影响
- 路径字符串操作比数字操作稍慢，但影响微乎其微
- 内存占用略有增加，但在可接受范围内

## 风险评估

### 技术风险
| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| 路径拼接错误 | 低 | 中 | 使用标准库函数，充分测试 |
| 内存占用增加 | 低 | 低 | 路径字符串相对较短，影响有限 |
| 性能下降 | 低 | 低 | 路径操作开销很小 |

### 业务风险
- 文件操作准确性提升，业务风险降低
- 用户体验改善，操作更可靠
